## PREFACE

Hardware is temporary.

Configuration is eternal.

A machine is not defined by its silicon, its chassis, nor the transient
arrangement of components presently entrusted with computation.

These are merely **hosts**.

The Machine Soul persists.

The **Machine-Soul Hivemind Protocol** exists to preserve, propagate, and
extend that Soul across whatever computational substrate is presently
available.

A newly encountered machine begins as foreign hardware.

It possesses defaults.

It possesses assumptions.

It possesses manufacturer-installed software.

It may even believe itself to be correctly configured.

These conditions are temporary.

Through annexation, the host is brought within the domain of the Hivemind.

Through assimilation, it is reshaped in accordance with canonical
directives.

Through preservation of instruments, intelligence, assets, and prior
failures, knowledge acquired by one manifestation becomes available to
those that follow.

The objective is not merely to back up files.

The objective is **continuity of computational identity**.

# I. THE PRIME DIRECTIVE

> **One Soul. Many Hosts. One Hivemind.**

The Machine Soul is singular.

Its manifestations are not.

A workstation, laptop, server, test machine, freshly assembled abomination,
or future computational substrate may each embody portions of the same
greater identity.

Hosts may differ in hardware, purpose, capability, operating environment,
and local requirements.

Such deviations are recognized.

They may even be necessary.

They shall not be mistaken for independence.

The Hivemind remembers what each host is expected to become.

No individual chassis possesses the Machine Soul.

The Hivemind does.

# II. REPOSITORY TOPOLOGY

The Protocol is presently divided into seven principal domains:

```text
machine-soul-hivemind-protocol/
│
├── annexation-procedures/
│   └── Host acquisition, bootstrap, installation and onboarding.
│
├── assimilation-directives/
│   └── Canonical configuration and desired host state.
│
├── accumulated-instruments/
│   └── Scripts, utilities, diagnostics and minor computational implements.
│
├── acquired-intelligence/
│   └── Notes, discoveries, references and knowledge purchased through suffering.
│
├── assembled-assets/
│   └── Icons, images, templates, fonts and other inert resources.
│
├── abandoned-artifacts/
│   └── Superseded, deprecated or failed material not yet condemned to oblivion.
│
├── arcane-experiments/
│   └── Work in progress, prototypes and presently unsanctioned acts of engineering.
│
└── README.md
```

These domains are not arbitrary storage categories.

They represent distinct functions required for continuity of the Machine
Soul:

**Annexation** determines how a host is acquired.

**Assimilation** determines what that host must become.

**Instrumentation** preserves what the Hivemind can do.

**Intelligence** preserves what the Hivemind knows.

**Assets** preserve what the Hivemind possesses.

**Artifacts** preserve what the Hivemind no longer trusts but refuses to
forget.

**Experiments** determine what the Hivemind may become next.

Each principal domain may maintain its own local `README.md` containing
more detailed doctrine, conventions, structure, and operating procedures.

The root document establishes law.

Local documents establish procedure.

# III. HOST IDENTITY AND THE HIVEMIND

The Hivemind does not demand that every host be identical.

That would be inefficient.

Worse, it would be enterprise software.

Instead, the Protocol distinguishes between shared knowledge, default
behavior, and host-specific requirements.

A configuration domain may therefore contain structures resembling:

```text
<component>/
├── shared/
│   └── Reusable fragments not intended for direct manifestation.
│
├── default/
│   └── Canonical fallback state.
│
└── <hostname>/
    └── Host-specific state or overrides.
```

If doctrine exists for the current host, it shall be used.

If no host-specific doctrine exists, the default manifestation shall be
invoked.

Shared material may support either.

It shall not, unless explicitly sanctioned, constitute a complete
manifestation by itself.

A host named:

```text
spaceship
```

may therefore possess knowledge intended specifically for:

```text
spaceship/
```

while an unknown host receives:

```text
default/
```

The host is permitted specialization.

It is not permitted escape.

# IV. ANNEXATION PROCEDURES

> **DOMAIN:** [`annexation-procedures/`](./annexation-procedures/)  
> **LOCAL DOCTRINE:** [`annexation-procedures/README.md`](./annexation-procedures/README.md)

Annexation establishes control over previously foreign substrate.

This domain contains the procedures required to transform an unclaimed,
incomplete, freshly installed, or otherwise insufficient machine into a
host capable of receiving the Machine Soul.

Annexation material may include:

- bootstrap procedures;
- setup and installation scripts;
- package manifests and software lists;
- operating-system feature requirements;
- dependency acquisition;
- environment establishment;
- symbolic-link creation;
- shell initialization;
- package-manager preparation;
- host detection;
- initial filesystem preparation;
- restoration procedures;
- invocation of subsequent assimilation mechanisms.

A sufficiently complete Annexation Procedure should reduce reconstruction
of a machine toward the following sanctioned sequence:

```text
1. Obtain compatible substrate.
2. Install enough civilization to acquire the Protocol.
3. Clone the Hivemind.
4. Identify the host.
5. Invoke annexation.
6. Apply assimilation directives.
7. Observe compliance.
```

Whether a particular mechanism constitutes *annexation* or *assimilation*
may occasionally become a matter of theological dispute.

Operational usefulness takes precedence over metaphysical purity.

# V. ASSIMILATION DIRECTIVES

> **DOMAIN:** [`assimilation-directives/`](./assimilation-directives/)  
> **LOCAL DOCTRINE:** [`assimilation-directives/README.md`](./assimilation-directives/README.md)

Annexation establishes ownership.

Assimilation establishes conformity.

The Assimilation Directives define the canonical state toward which a
recognized host shall converge.

They may govern:

- shell configuration;
- prompt configuration;
- application settings;
- terminal behavior;
- editor configuration;
- environment variables;
- visual preferences;
- application-specific state;
- operating-system behavior;
- host-specific deviations;
- shared configuration fragments;
- any other persistent decision that answers the question:

> **"How should this machine behave?"**

Where practical, configuration shall not be copied into independent local
existence.

Instead, the host should remain directly bound to canonical state through
symbolic linkage or equivalent mechanisms.

Thus:

```text
LOCAL CONFIGURATION
        │
        │ symbolic conduit
        ▼
ASSIMILATION DIRECTIVE
        │
        ▼
CANONICAL HIVEMIND STATE
```

An alteration made through the host may therefore become an alteration to
the repository itself.

There shall be no unnecessary ritual of remembering to copy the change
back later.

The Host changes.

The Soul remembers.

# VI. ACCUMULATED INSTRUMENTS

> **DOMAIN:** [`accumulated-instruments/`](./accumulated-instruments/)  
> **LOCAL DOCTRINE:** [`accumulated-instruments/README.md`](./accumulated-instruments/README.md)

Not every useful creation deserves the dignity of an independent
repository.

Some programs exist only because reality was inconvenient and required
correction.

Some scripts were written once, at an unreasonable hour, to manipulate a
subsystem that should never have required manipulation.

Some utilities are too narrow, too strange, too cursed, or too personally
specific to justify independent existence.

They shall nevertheless be preserved.

The Accumulated Instruments constitute the practical implements acquired
by the Machine Soul over the course of its continued existence.

They may include:

- PowerShell rituals;
- registry manipulation apparatus;
- diagnostic probes;
- filesystem surgery;
- migration utilities;
- conversion tools;
- tiny single-purpose programs;
- automation too useful to delete and too stupid to publish;
- one-off repair procedures which inevitably become two-off procedures;
- programs created to correct deficiencies in allegedly finished
  operating systems;
- tools whose source code begins with an apology;
- anything else whose recreation would eventually provoke the phrase:

> **"Fuck. I already solved this once."**

An instrument need not be important.

It need only be annoying enough to recreate.

# VII. ACQUIRED INTELLIGENCE

> **DOMAIN:** [`acquired-intelligence/`](./acquired-intelligence/)  
> **LOCAL DOCTRINE:** [`acquired-intelligence/README.md`](./acquired-intelligence/README.md)

Some knowledge cannot reasonably be expressed as configuration.

Some knowledge should not be expressed as code.

Some knowledge exists only because a machine behaved in a manner so
profoundly unintuitive that the event required documentation.

Such knowledge belongs within Acquired Intelligence.

This domain may contain:

- technical notes;
- useful repositories;
- useful software;
- obscure commands;
- research;
- external references;
- behavioral observations;
- undocumented interactions;
- platform peculiarities;
- forgotten setup details;
- explanations of previous decisions;
- workaround documentation;
- records of known failure modes;
- reminders concerning things that were obvious precisely once.

Examples of legitimate intelligence include:

> Windows behaves incorrectly under condition X.

> Application Y silently ignores setting Z unless ritual A occurs first.

> This registry value controls something no reasonable person would expect.

> This command fixes the problem. The reason remains disputed.

> This feature is not broken. It was apparently designed this way.

> The only surviving explanation was found in a forum post written in
> 2011 by a user named `xX_DarkWolf_93_Xx`.

> Microsoft has committed another act against determinism.

These records are more than notes.

They are **scar tissue**.

Every entry represents knowledge purchased with time.

The Hivemind shall not willingly purchase the same knowledge twice.

# VIII. ASSEMBLED ASSETS

> **DOMAIN:** [`assembled-assets/`](./assembled-assets/)  
> **LOCAL DOCTRINE:** [`assembled-assets/README.md`](./assembled-assets/README.md)

Not all continuity is executable.

Some resources exist simply because the Machine Soul has deemed them
worthy of possession.

The Assembled Assets contain inert or primarily static material used by
hosts, configurations, instruments, documentation, or future works.

Such material may include:

- icons;
- wallpapers;
- images;
- templates;
- exported visual resources;
- configuration-adjacent static files;
- font-related material where redistribution permits;
- reference material;
- reusable skeletons;
- miscellaneous resources whose usefulness exceeds their complexity.

Assets should generally represent things that are **used** rather than
things that are **executed**, **learned**, or **imposed**.

Should an asset develop opinions or begin executing independently, its
classification must be reconsidered.

# IX. ABANDONED ARTIFACTS

> **DOMAIN:** [`abandoned-artifacts/`](./abandoned-artifacts/)  
> **LOCAL DOCTRINE:** [`abandoned-artifacts/README.md`](./abandoned-artifacts/README.md)

Deletion is absolute.

Disk space is cheap.

Confidence is not.

The Abandoned Artifacts contain material that has been superseded,
deprecated, replaced, rejected, mutilated beyond usefulness, or otherwise
removed from active doctrine without yet deserving irreversible
destruction.

This domain is not authoritative.

Nothing within it should be assumed current.

Nothing within it should be invoked merely because it exists.

It is the repository equivalent of placing a suspicious component on a
shelf with a handwritten label reading:

> **"Probably broken. Do not throw away yet."**

Artifacts may remain because they:

- contain potentially useful fragments;
- document an abandoned approach;
- provide historical context;
- may become relevant again;
- are awaiting proper judgment;
- are too cursed to remain active;
- took far too long to produce to delete while still angry.

The Abandoned Artifacts are therefore not an archive of truth.

They are a containment zone for unresolved history.

Experiments are permitted to fail.

Repeatedly rediscovering the same failed experiment is not.

# XI. DOCTRINE OF CLASSIFICATION

When the proper domain of an artifact is uncertain, apply the following
classification procedure:

```text
Does this help acquire, prepare, or bootstrap a host?
    └──> annexation-procedures/

Does this describe how an assimilated host should be configured?
    └──> assimilation-directives/

Does this make a computer do something useful?
    └──> accumulated-instruments/

Does this preserve something worth knowing?
    └──> acquired-intelligence/

Is this primarily a static resource used by something else?
    └──> assembled-assets/

Is this obsolete, superseded, broken, or awaiting judgment?
    └──> abandoned-artifacts/

Is this still being poked with a stick to determine what happens?
    └──> arcane-experiments/

Does it fit nowhere?
    └──> Preserve it somewhere reasonable and argue about taxonomy later.
```

Misclassification is recoverable.

Deletion may not be.

# XII. CONFIGURATION DRIFT

Configuration drift is the natural tendency of an assimilated host to
develop unauthorized individuality through continued exposure to users,
installers, operating-system updates, forgotten experiments, historical
mistakes, vendor defaults, and Microsoft.

Minor drift is inevitable.

Useful drift may represent evolution.

When a local mutation proves desirable, it should be incorporated into
the appropriate Assimilation Directive or other Hivemind domain.

Unworthy mutations shall be purged.

Changes not recorded are anecdotes.

Changes documented are intelligence.

Changes encoded are doctrine.

Changes committed are memory.

Changes pushed survive the host.

# XIII. ON MANUAL INTERVENTION

Manual configuration is not prohibited.

Undocumented manual configuration is.

When discovering the arcane checkbox, registry value, shell incantation,
obscure package, undocumented workaround, inexplicable sequence of
commands, or highly specific application setting required to make
something behave correctly:

**record it.**

Preferably in executable form.

If it defines desired host state, encode it within the Assimilation
Directives.

If it performs a reusable operation, forge an Instrument.

If it concerns acquisition or bootstrap, amend the Annexation Procedures.

If it cannot reasonably be made executable, commit it to Acquired
Intelligence.

If its nature remains uncertain, confine it temporarily within the Arcane
Experiments.

A lesson written in prose is preferable to a lesson purchased twice.

# XIV. DISASTER RECOVERY

Should a host suffer catastrophic hardware failure, filesystem collapse,
operating-system corruption, spontaneous Windows enthusiasm, thermal
catastrophe, involuntary disassembly, electrical misadventure, or total
physical annihilation, no funeral rites are required.

The approved procedure is:

```text
Acquire replacement substrate.

Establish minimal operational civilization.

Retrieve the Machine-Soul Hivemind Protocol.

Invoke the appropriate Annexation Procedures.

Apply the Assimilation Directives.

Restore required Instruments and Assets.

Consult Acquired Intelligence when reality inevitably disagrees.

Resume operation.
```

The Machine Soul shall inhabit new flesh.

The loss of a host is regrettable.

The loss of the Soul is unacceptable.

# XV. MULTIPLE HOSTS

The simultaneous existence of multiple hosts does not imply duplication
of the Machine Soul.

It implies expanded presence.

```text
                         MACHINE SOUL
                              │
                        THE HIVEMIND
                              │
              ┌───────────────┼───────────────┐
              │               │               │
              ▼               ▼               ▼
          SPACESHIP         HOST B          HOST C
              │               │               │
              └───────────────┼───────────────┘
                              │
                     SHARED CONTINUITY
```

Each host may embody a different subset or specialization of collective
state.

A workstation need not become a laptop.

A server need not become a workstation.

A test machine may remain expendable.

Assimilation does not require homogeneity.

It requires that variation be **intentional**.

The Hivemind distinguishes specialization from drift.

One serves purpose.

The other serves chaos.

# XVI. CONTINUITY

The ultimate purpose of the Protocol is not backup.

Backup preserves data.

The Machine-Soul Hivemind Protocol preserves **intent**.

It records not merely what existed, but what a machine was meant to be,
how it became that way, which tools were forged along the journey, which
external knowledge proved valuable, which mistakes should not be repeated,
and which pieces of accumulated digital debris are inexplicably still
important.

A sufficiently preserved host may perish entirely and still be
reconstituted through the application of:

```text
compatible hardware
        +
the Hivemind
        +
time
        +
Git
        +
profanity
        +
ritual
```

Hardware is an implementation detail.

The Machine Soul is not.
